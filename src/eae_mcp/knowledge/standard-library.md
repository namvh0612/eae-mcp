# Standard library, runtime blocks and generic FBs

How to pick building blocks. Use `eae_library_guide` for what a solution actually contains and uses;
use `eae_get <type>` for exact pins. Library pins have no IDs: networks reference them by name.

## IEC 61499 standard event FBs (`IEC61499.Standard`, library Runtime.Base)

Defined by IEC 61499-1 Annex A. They route, time and gate **events**; put data logic in Basic FBs.

| FB | Pins | Use it to |
|---|---|---|
| E_SPLIT | EI → EO1, EO2 | fire several events in a fixed order |
| E_MERGE | EI1, EI2 → EO | join event paths (OR) |
| E_REND | EI1, EI2, R → EO | rendezvous: EO once both arrived; R resets |
| E_PERMIT | EI, PERMIT → EO | pass EI only while PERMIT = TRUE (interlock, enable) |
| E_SWITCH | EI, G → EO0 / EO1 | route by a BOOL (if/else on events) |
| E_SELECT | EI0, EI1, G → EO | pass EI0 or EI1 depending on G |
| E_DEMUX | EI, K → EO0…EOn | route by an index |
| E_DELAY | START, STOP, DT → EO | one delayed event; a new START while running is ignored |
| E_CYCLE | START, STOP, DT → EO | periodic event every DT until STOP |
| E_TRAIN / E_TABLE / E_N_TABLE | START, STOP, DT, N → EO, CV | finite trains or tables of timed events |
| E_RESTART | → COLD, WARM, STOP | react to resource start/stop |
| E_SR / E_RS | S, R → EO, Q | event-driven set/reset flip-flop (EO when Q changes) |
| E_D_FF | CLK, D → EO, Q | latch D on CLK |
| E_R_TRIG / E_F_TRIG | EI, QI → EO | event on rising / falling edge of a sampled BOOL |
| E_CTU | CU, R, PV → CUO, RO, CV, Q | event counter |

Rules of thumb:
- Never build a loop of events without a delay (E_CYCLE/E_DELAY) in it: it blocks the resource.
- One event per pin per connection; use E_SPLIT for fan-out when order matters.
- E_PERMIT/E_SWITCH take their data input sampled at the event: wire the BOOL with the same event chain
  that updates it, or the previous value is used.

## EAE runtime blocks (inferred from pins and usage; confirm with `eae_get`)

| Block (namespace) | Pins | Purpose |
|---|---|---|
| E_DELAYR (Runtime.Standard) | RESTART, STOP, DT → EO | re-triggerable delay (watchdog/timeout: each RESTART restarts DT) |
| EVENTCHAINHEAD (Runtime.Standard) | INIT, TRIGGER → INITO, FINISHED; NAME | head of a named, ordered initialisation chain |
| EVENTCHAIN (Runtime.Standard) | ACK → EO; NAME, PRIO | member of the chain NAME; fired in PRIO order, acknowledges with ACK |
| DPAC_FULLINIT (SE.DPAC) | INIT, OC_RETRIGGER → INITO, OC_DONE | full dPAC initialisation before the application starts (needed with OPC UA) |

Typical init pattern (SE.Agile `INIT_v1_0`): one EVENTCHAINHEAD per phase ('Interfaces', 'Comms',
'Equipment', 'Other'); every CAT that needs ordered start-up contains an EVENTCHAIN with that NAME and a
PRIO, so start-up order is configured by parameters instead of wires.

## Generic FBs (parameterised library templates)

A type such as `VALFORMAT_8708B18B173C5ABA` is a **concrete instance of a generic template** (`VALFORMAT`)
generated by EAE for one parameter set. The FB carries
`<Attribute Name="Configuration.GenericFBType.InterfaceParams" Value="Runtime.Standard#I:=1;VALUE${I}:STRING" />`:
the template's library, the counts (`I:=1`) and pin patterns with their types (`VALUE${I}:STRING` →
`VALUE1 : STRING`). The hash suffix depends only on the full parameter string, library included (so
SYMLINKMULTIVARSRC and SYMLINKMULTIVARDST with the same parameters share a suffix, while VALFORMAT from
Runtime.Standard with the same pins gets another), and concrete types are generated per project (namespace `Main` in the main project, `SE.Agile` inside that library).

Families seen in practice:

| Template (library) | Parameters | Purpose |
|---|---|---|
| VALFORMAT (Runtime.Standard) | `I`, `VALUE${I}` | printf-style formatting: FORMAT ('%s'), VALUE1..n → RESULT on REQ/CNF |
| BUFFER (Runtime.Standard) | `CNT`, `DIN${CNT}` | buffer/queue of typed values |
| PERSISTENCE (Runtime.Standard) | `I`, `input${I}` | keep values over restarts: INIT, READ/READCNF, WRITE; default${I}, output${I} |
| JSON_PARSER / JSON_BUILDER (Runtime.Standard) | `CNT`, `valueOut${CNT}` / `value${CNT}` | parse/build JSON (payload, SET_PATH, PARSE → valueOut/typeOut) |
| AND, NOT, DS_SELECTX (Runtime.Standard) | `CNT`, `CNTX`/`CNTY` | n-input logic and data selectors |
| SYMLINKMULTIVARSRC / ...DST (Runtime.System) | `I`, `VALUE${I}` | symbolic links: publish (SRC) / subscribe (DST) a set of values by NAME across FBs/resources |
| MIBGET (Runtime.System) | `CNT`, `INDEX${CNT}` | read runtime management (MIB) values |
| MQTT_PUBLISH / MQTT_SUBSCRIBE (Runtime.NetConnectivity) | `CNTX` | MQTT topics: INIT, PUBLISH1(Topic1, Payload1, Retain1) |
| NETIO (Runtime.IoCommon) | `I`, `SD`, `RD` | raw network I/O with typed send/receive buffers |
| OPCUA_READ / OPCUA_WRITE (Standard.OPCUAClient) | `CNTX`, `VALUE${CNTX}` | OPC UA client read/write |

With eae-mcp: `eae_generic_fbs` lists the concrete types, parameters and **pins learned from existing
connections**; `eae_net_add_fb type="VALFORMAT" generic_params="I:=1;VALUE${I}:STRING"` reuses the
concrete type. A parameter set never used in the solution must be created once in EAE (the hash cannot be
computed outside EAE).

## Path macros in parameters

Parameters of symbolic-link and naming FBs use `$${PATH}` macros, expanded by EAE per instance, e.g.
`'$${PATH}IOSignal'` or `'$${PATH:-3,1}'` (a slice of the instance path, counted from the end). They let one
CAT type produce unique names per instance; `$$` escapes `$` inside an ST string literal.

## Choosing between library and own types

1. Search first: `eae_library_guide query="valve"`; prefer the highest `_vX_Y` of a family
   (`superseded: true` marks older versions).
2. Prefer a CAT from the library when one exists (it brings HMI symbols and OPC UA config).
3. Build your own Basic FB only for logic, a Function for a reusable stateless calculation, a Composite to
   wire FBs together, a CAT when you also need an HMI face.
